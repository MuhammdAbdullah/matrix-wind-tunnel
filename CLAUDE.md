# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Scope and git boundary

This directory is its own independent Git repository (`matrix-wind-tunnel`) — the new Windows Electron app combining **Wind Tunnel Control** and **Wind Tunnel Calibrator**. Commit and push only from here. **All code changes belong in this folder only.** The sibling folders one level up (`Firmware/`, `Matrix Wind Tunnel 2.2/`, `Process Control V2/`) are **read-only reference material** — never edit, add, or remove files inside them, and they are never part of this repo's commits. See `../AGENTS.md` for the full behavioral spec those references define (protocol tables, experiment/graph rules, Admin requirements, firmware constraints). Read that file before implementing any protocol, calibration, or experiment behavior; this CLAUDE.md only covers what's inside this repo.

Never modify the firmware files (outside this repo). There is **no "approved" firmware image**: the firmware is still in development and **V2.0.7 is the latest** (`Firmware/WindTunnel V2.0.7.*`); the app targets it (`LATEST_FIRMWARE_VERSION` in `main/firmware.js`). **The image to run on the controller is `../Firmware/Socket fix/B-nousb - fallback with USB check off/` (owner's decision 2026-11-04): V2.0.7 with the Ethernet socket fix, queue flush, USB-read guard, 5-10 s stale-session drop (`PingIdle` 25) and the USB-live check disabled (`WT_USB_LIVE_LOOPS = 0`, so `auth:2` never happens from it). Treat it as the latest firmware for Ethernet work; the plain `Firmware/WindTunnel V2.0.7.*` files are the older, unfixed build.** The only firmware-file naming rule is that a `.hex` loaded in Admin → Bootloader must have a name **starting with `WindTunnel`** (case-insensitive, anything after it allowed); other names are rejected before the file is opened (`HEX_NAME_PREFIX`, `loadHex()` in `main/firmware.js`).

## Commands

```powershell
npm install
npm start            # Electron desktop app — auto-scans for real USB hardware
npm run simulate      # Electron with --simulate flag (synthetic sensor data, no hardware needed)
npm run dev           # Electron with --dev flag
npm run build-win     # electron-builder Windows NSIS installer -> dist/
npm run rebuild-hid   # electron-rebuild node-hid against Electron's ABI (needed after npm install / Electron bump if HID fails to load)
```

`build-mac` / `build-linux` also exist; `.github/workflows/release.yml` builds all three platforms on `v*` tags (or manual dispatch). Linux needs the udev rules in `docs/99-wind-tunnel.rules` (VID `0x12BF`) installed for serial/HID access.

There is no automated test suite and no lint config. Verify changes by running `npm run simulate` (no hardware) or `npm start` against a real controller, and by manual checks against `../AGENTS.md`'s protocol/behavior tables.

## Architecture

Main-process logic is split into `main/` modules, required from a slim orchestrating `main.js` (window creation + `ipcMain.handle` registration only). The renderer has no bundler/build step — `renderer/index.html` loads `charts.js` then `app.js` directly via `<script>` tags, plus Chart.js from a CDN.

**Process boundary**: `contextIsolation: true`, `nodeIntegration: false`. The renderer never touches `serialport` directly — it only calls `window.windTunnel.*` (defined in `preload.js`), which maps 1:1 to `ipcMain.handle` channels in `main.js`. When adding a new hardware/experiment/calibration/Admin operation, add it in four places: the logic in the relevant `main/*.js` module, an `ipcMain.handle` in `main.js`, a matching method in `preload.js`, and the call site in `renderer/app.js`.

**Module dependency direction** (no circular requires): `state.js` and `protocol.js` are leaves; `serial.js` depends on both; `logging.js` depends on `state.js`; `sweeps.js` depends on `serial.js` + `logging.js` + `experiments.js`; `calibration.js` depends on `serial.js` + `admin.js`; `bootloader.js` is a leaf (own HID transport, no dependency on `serial.js` -- the bootloader is a distinct USB HID identity/protocol from the running application's serial link); `firmware.js` depends on `bootloader.js` + `admin.js` + `state.js` (for `pushEvent`). Cross-module reactions (e.g. "stop the sweep on an unexpected disconnect") go through `serial.onUnexpectedDisconnect(listener)` rather than `serial.js` requiring `sweeps.js` back — keep new cross-cutting hooks in that direction (the dependent module registers a listener on the module it depends on, never the reverse).

### State and push updates

`main/state.js` holds one `state` object (connection status, simulation flag, fan/angle, sensors, diagnostics, `experimentId`, `tapping`, `dragShape`, `customAxes`, `sweep`, `logging`, `adminUnlocked`). Every mutation calls `publish()`, which recomputes `state.adminUnlocked` from `admin.isUnlocked()` and pushes the whole object to the renderer via the `state:update` IPC event. `pushEvent(channel, payload)` is the generic one-off push used by `logging.js` (`log:event`) and `firmware.js` (`firmware:progress`); `appendAudit()` also uses it for `audit:update`. The renderer has no independent source of truth — `render(value)` in `app.js` re-derives all DOM text/charts from each pushed snapshot. Renderer-only state (sample buffers for charting, which experiment object is selected, pending hex file path) is fine locally; don't duplicate anything `main/state.js` already tracks authoritatively.

### Serial transport, command queue, and reconnect

- USB identity: VID `0x12BF`, PID `0xF010`; baud `115200`. `serial.startAutoConnect()` polls `SerialPort.list()` every 2s while disconnected.
- Wire format: the V2.0.7 application firmware (V2.0.6 behaved the same) speaks flat JSON objects (`{"readsensors":0}` -> `{"lift":..,"drag":..,"pressure":..,"velocity":..}`), built in `serial.js`'s `jsonRequestFor()`; `handleData()` buffers incrementally, takes the object ending at the first `}` (resynchronising past truncated garbage) and caps the buffer. A reply only resolves the pending command if it carries every key for that command as a finite number (`RESPONSE_KEYS`), so a late or partial object can never overwrite valid readings. `main/protocol.js`'s `frame()`/`parseFrames()` binary framing is no longer used by the transport; only its `CMD` map is.
- `sendBinary(command, payload, {timeout, retries, source, handshake, audit})` chains onto a single `commandQueue` promise so only one command is ever in flight. It fails immediately (a `LinkError`, never retried) when the link is down, unless `handshake: true` (connect-time version read). Queued work captures `linkGeneration` and refuses to run against a later session, so stale commands can never replay onto a reconnected port. **The chain is deliberately re-armed with `.catch(() => {})` after every attempt** -- don't remove that line. Timeout/write callbacks compare `pendingCommand` by identity so an old attempt can't clear a newer one. `source` (`'control'|'calibrator'|'system'`) is recorded in the audit log; commands with no reply (fan, angle, LED, zero, set-*) are audited as `sent`, not `ack`, because only the OS write was confirmed.
- `API_VERSION = 2` is verified by `openSession()` (via `connectHardware()`, used by manual connect and the scanner). `state.connected` is set **only after** the version reply passes (`state.connecting` covers the handshake, which allows ~9 s because the firmware API comes up 3-4 s after the COM port appears). A failed handshake closes the port without notifying `onUnexpectedDisconnect`.
- Link loss: `markLinkLost(reason, port)` is the single exit for an unexpected end of session (port `close`/`error`/`end`, write failure, watchdog expiry). It is bound to the specific port (events from superseded handles are ignored via `port !== serialPort`), bumps `linkGeneration`, rejects the pending command, resets the queue, closes the handle, then notifies `onUnexpectedDisconnect` listeners and requests a rescan. **Touchscreen change reports** (`applyTouchUpdate()` in `serial.js`, **needs the touchscreen-JSON firmware build -- `SyncTouchStatus` in `../Firmware/WindTunnel V2.0.7.fcfx`, not yet compiled or run on hardware**): that firmware pushes `{"fanspeed":n}`, `{"angle":n}`, `{"animmode":..,"animr":..,"animg":..,"animb":..}` and the `amb*` equivalent when a touch press changes them. `handleData()` mirrors them into `state.fanSpeed`/`angle`/`leds` and `publish()`es (the renderer already redraws sliders, numbers and LED pickers from state) *before* the pending-command logic, so they never resolve or disturb a pending command. **Watchdog** (`watchdogTick`, 500 ms): apart from those reports the firmware sends nothing unsolicited, so liveness is time since the last valid reply (`lastRxOkAt`). A VERSION heartbeat is sent when silent >= 1.5 s and nothing is queued; `state.linkDegraded` is set at 3 s; the link is declared lost at 8 s (`LINK_LOST_MS`, deliberately above the firmware's ~5 s touch-hold service gap). `WATCHDOG_GRACE_MS` extends the window after commands the firmware can legitimately stall on (network 10 s, EEPROM writes 3 s). Recovery: `scanOnce()` (2 s interval, plus a 500 ms kick after a loss) lists ports and matches VID/PID every time -- it does not retry the old COM path, because Windows may renumber it -- with 0.5 s..4 s backoff after failed attempts. `open()`/`close()` are time-limited so a wedged driver call can't block recovery. `disconnect()` (manual) is not reported as unexpected, but the scanner will reconnect within ~2 s; `main.js` stops any sweep first. `enterSafeState(source, {preempt:true})` (used on quit) abandons queued work so fan-off is written immediately. Set `WIND_TUNNEL_SERIAL_DEBUG=1` for per-chunk RX logging.

### Ethernet and remote access (V2.0.7)

Source for all of this: `../Firmware/WindTunnel V2.0.7.fcfx` and `../Firmware/WindTunnelAPI 1.xlsx`. **Not yet verified on real hardware** -- only against a mock WebSocket controller.

- **Controller side (V2.0.7):** the W5500 now serves the JSON API over a **WebSocket server** (`WebSocket1`, `CreateServerSocket(EthPort)`, default port **1245**), not raw TCP. One text message per request/reply (`SendText`). Only JSON is parsed now (the `:cmd;` binary frames were removed from `APIActionCommand`). DHCP is **on by default**. `ip0`-`ip3`, `port` and the new `dhcp` flag are stored in EEPROM (bytes 36-39, 40, 41); the firmware re-applies them (DHCP_Run blocks ~5 s, or SetMyIP) and re-creates the WebSocket server **only when `dhcp` is present**, so `jsonRequestFor(SET_NETWORK)` always sends it. The command sends **no reply**, so `calibration.setNetwork` reports `sent`, never `acknowledged`. V2.0.7 as built cannot report its IP over the API (the DHCP address is on the touchscreen Settings page); firmware with the access-control patch can (`netinfo`/`macinfo`, see below).
- **Verified on real hardware (2026-10-29, controller at 192.168.1.150, MAC 00-08-DC = W5500):** the WebSocket API on port 1245 works as described (`{"version":0}` -> `{"version":2}`, `{"readsensors":0}` -> four floats), one text message each way. **The controller serves exactly one client and only frees the socket on a proper WebSocket close handshake.** A client that disappears abruptly (process killed/Ctrl-C, `ws.terminate()`) makes the controller answer `ECONNREFUSED` for ~23 s before it listens again; graceful closes reconnect immediately. So never `terminate()` an open Ethernet socket: `EthernetPort.close()`, `probe()` and the quit path (`serial.closeLink()`, awaited in `main.js` `before-quit`) all close politely. A refused connection right after a crash is expected for ~25 s; the scanner keeps retrying.
- **Firmware has no master/client concept:** `APIReply` answers whichever source (`CommsSource`) put the last byte in the shared buffer, and nothing can make a client read-only. That is why view-only/control is enforced by the relay in this app, not by the controller. A client that opens the controller's WebSocket directly bypasses it -- keep the controller on a trusted network.
- **`main/ethernet.js`:** `EthernetPort` wraps a `ws` client in the slice of the SerialPort interface `serial.js` uses (open/write/close/isOpen, `data`/`error`/`close`), so the single command queue, retries, watchdog and handshake are shared. Also `probe()` for the Admin network scan.
- **USB is always the master link (`serial.js` `scanOnce`):** Ethernet is only a fallback when no USB controller exists (`serial.setEthernetTarget`, set from the saved Admin settings). While on Ethernet the scanner keeps listing USB ports; when the controller appears it calls `markLinkLost(...)` (which stops any sweep via the disconnect listeners) and connects USB. `state.transport` is `'usb' | 'ethernet' | 'remote' | null`.
- **`main/network.js`:** settings in `wind-tunnel-config.json` under `network` (via `main/config.js`, which merges so `logging.js`' `logsFolder` is not clobbered). **Relay (master):** an HTTP + WebSocket server on `0.0.0.0:<relay port, default 8090>` while a hardware link exists and mode != `off`. Clients must send `{type:'hello', code}` within 5 s (random 8-char code, constant-time compare, 5 failures -> 60 s lockout per IP, max 8 clients, 4 KB messages). Mode is `off | view | control` and is **re-read on every command**, so switching to view-only takes effect on live sessions. Allowed commands are only those in `RELAY_COMMANDS` (fan, angle, LEDs, zero sensors/motor, stop sweep) and run through `main/control.js`, the same code the local IPC handlers use; fan/angle/zero-motor are refused while the master runs a sweep. Sweeps, logging, calibration, firmware and Admin are never reachable remotely. State is broadcast via `state.onPublish`, throttled to 100 ms, using a whitelisted `snapshot()` (no diagnostics/log paths/Admin state). The browser page is `renderer/remote/` (served from a two-file whitelist, `no-store`, strict CSP).
- **Remote client (this app -> another master):** `connectRemote` stops sweeps, disconnects local hardware, stops the relay and sets `state.transport = 'remote'`; the master's snapshot is mirrored into `state` (not experiment/logging/sweep fields). It stays in `'remote'` mode while reconnecting so the local scanner cannot take the hardware. `control.js` forwards fan/angle/LED/zero to the master (`setRemoteForwarder`); `sweeps.js`' sensor timer, `calibration.js` `guard()` and the sweep/log IPC handlers refuse in remote mode. Quitting a remote client never touches the master's fan. The access code is not persisted (re-enter per session).
- **Who is master on the LAN (`network.js` discovery):** the controller itself admits one Ethernet client, so with no USB the first app to connect over Ethernet *is* the master (its relay serves everyone else). Each app that owns the hardware link (USB, or Ethernet) broadcasts a UDP beacon every 2 s on port 8091 (`{app:'wind-tunnel-master', id, name, port, mode, hardware}`, no secrets; announced even when the relay is `off` so USB can still win). Other apps list live masters (7 s TTL) in Admin -> Network with a "Use" button; the access code is still required. **USB always wins across PCs:** an app holding the controller over Ethernet that hears a `hardware:'usb'` beacon releases the link gracefully (`serial.setEthernetYield`, `state.network.ethernetYield`) and does not retry until the beacon disappears, then reconnects by itself. The beacon is unauthenticated, so a spoofed one on the LAN can make an Ethernet master step aside (the controller port itself has no authentication either).
- **Controller resets every Ethernet connection (2026-11-03, unresolved until flashed and checked on hardware):** the unit at 192.168.1.150 accepted TCP but dropped every client with `ECONNRESET` before the WebSocket upgrade (LAN and direct cable; both the current build and the pre-access-control build). Packet captures showed the W5500 killing the socket, not the request being rejected. Causes found in the firmware source: (1) the WebSocket component's accept loop re-creates the W5500 socket on every main-loop pass and destroys a just-accepted connection (fixed and confirmed on hardware: the `101` upgrade now completes); (2) the W5500 driver never releases received bytes (`Sn_RX_RD`/`RECV` never written), so the frame reader re-reads the old HTTP request and answers the first client frame with a close frame, and junk without CRLFCRLF would hang the main loop. Fix for both (new `EthPoll` macro, two ready images, `apply.js`, host harness): `tools/firmware-socket-fix/README.md`, images in `../Firmware/Socket fix/`. **Confirmed on hardware 2026-11-03** (direct cable, USB unplugged, power-cycled, image = fix with the USB-live check disabled): full `hi`/`hey`/`com`/`ok` handshake, `version` -> 2, `readsensors` values, and this app connected over Ethernet ("Connected, API version 2") and stayed up. **Likely root cause of the intermittent behaviour (found later the same day, fix built but not yet confirmed on hardware):** with no USB cable the controller replays stale USB commands forever (`getsUSBUSART` with a null descriptor handle returns its old receive buffer on every call; a recorder build showed 186 Ethernet frames vs 2476 parsed messages, recent ones all USB-sourced `zeromotor`/`version`). That keeps the main loop and stepper busy, fakes a live USB host and pollutes the command queue; `EthPoll` now turns USB reads off unless `USBDeviceState` is CONFIGURED. See `tools/firmware-socket-fix/README.md`. **Correction, same day:** the app did NOT stay up. Its log showed `Link lost: no valid reply from the controller for 11s`. Scripted sessions showed why: replies were out of step with requests (a heartbeat `version` or `macinfo` was answered with a sensor reading, and the Hi/COM gate sometimes saw an old message and answered `auth:0`), because `ParseJSON` answers the message at the front of the shared command queue and stale messages from earlier traffic stay there (nothing clears the queue, and it only advances one message per new frame). `EthPoll` therefore also empties the queue (`FlushBuffer` + `COMMSSTATE = 0`) when a client connects or leaves, when a frame arrives and when the socket is re-opened; images rebuilt with this are not yet flashed or tested. Still open: (a) with the USB-live check enabled (`WT_USB_LIVE_LOOPS = 120`) the controller answered `{"auth":2}` on every attempt on 2026-11-03 even though no USB device was visible to the PC, so that gate is unproven; the clean image with it off is `Socket fix/B-nousb`; (b) the controller occasionally sends a duplicate reply (the app logs "Ignoring stray JSON response"); (c) after each client it pauses ~5 s (DHCP renew after a rejected/closed client) and refuses connections meanwhile; (d) earlier in the session the controller processed `version`/`zeromotor` commands nobody on the cable had sent (cause not found; USB-sourced is the suspect). Older notes: fix (2) was at that time not yet confirmed on hardware; when it is, update this entry and drop the "unresolved" wording. **Reconnect timing (2026-11-04, B-nousb flashed; app side changed, not yet re-measured on hardware):** unplugging and replugging the cable made the app take long or fail to reconnect, with `The controller did not accept the connection` (`auth:0`) in the log. The app's quiet periods were still sized for the legacy socket (25 s after a lost Ethernet session, 10 s after a failed open, 15 s after an auth refusal), which B-nousb does not need: `serial.js` now waits 2 s after a lost session (`ETHERNET_LINK_RECOVERY_MS`) and retries failures after 1.5 s doubling to 8 s (`ETHERNET_RETRY_BASE_MS`/`ETHERNET_RETRY_MAX_MS`; `ETHERNET_BLOCKED_BACKOFF_MS` 3 s is a floor for `auth:0`). A dead cable is still only noticed after `LINK_LOST_MS` (8 s) and the controller needs its own 5-10 s to drop the old session, so expect roughly 10-20 s end to end; the controller answers a refused connection harmlessly meanwhile. **Ping-assisted tracking (2026-11-04, `main/reach.js` + `reachTick()` in `serial.js`, not yet run on hardware):** a network cable gives no unplug signal (USB does), so Ethernet used to be noticed only after `LINK_LOST_MS` and a connect attempt to a still-unreachable controller hung up to 8-15 s before the next could start. The W5500 answers ICMP in hardware even while the main loop is busy, so every 700 ms the app pings the controller when it is disconnected, or when connected and the API has been silent >= 2 s: two failed pings end the link at once (~3-4 s instead of 8 s), connect attempts are skipped while ping fails (still one every 10 s), and the first ping reply triggers an immediate reconnect with the backoff reset. It only acts on ping once the host has answered a ping at least once (`reachSeenFor`), so a network that filters ICMP behaves exactly as before. The PC can have Ethernet and Wi-Fi on the same /24, so PC-adapter state is deliberately not used. If `auth:0` keeps appearing on every attempt, capture the controller side (see the debugging tip) rather than lengthening the backoff again. Debugging tip learnt here: Windows hides data that arrives just before an RST, so use `pktmon` (elevated) rather than a client library to see what the controller actually sent.
- **Ethernet access control + network identity** (app side written 2026-11-03, simplified the same day from a per-controller-key challenge/response to a fixed handshake; the firmware side is the edited-in-place `../Firmware/WindTunnel V2.0.7.fcfx`, **NOT compiled or run on hardware**; contract in `docs/ethernet-access-control.md`). USB is trusted and always wins; the controller refuses/drops Ethernet clients while a USB host is talking to it. `EthernetPort.open()` sends `{"hi":1}` as soon as the socket opens, answers `{"hey":1}` with `{"com":1}` and only succeeds on `{"ok":1}`. There is **no key**: the operator reads the controller's IP off its touchscreen and types it in. This is anti-accident/anti-casual-client protection, not security: the words are fixed and public. Handshake frames are intercepted and never reach `data`; no `hey` within 1.5 s = legacy firmware, continue unauthenticated; ~6 s budget. `{"auth":0|2|4}` become errors with `.code` `AUTH_FAILED|USB_IN_CONTROL|AUTH_TIMEOUT` and `.isAuth`; the socket is always closed politely. `serial.noteEthernetBlocked()` stores them in `state.network.ethernetBlocked` and backs the scanner off 15 s (`ETHERNET_BLOCKED_BACKOFF_MS`); a successful Ethernet connect clears it. A late `{"auth":2}` (USB took over mid-session) arrives as an `error` event -> `markLinkLost`. Firmware side: a client that fails the handshake is dropped and the controller re-runs DHCP (at most once per ~30 s; the router decides whether the IP actually changes), so the saved IP can go stale: the banner then tells the operator to re-read the touchscreen. New JSON commands `netinfo` and `macinfo` (string replies: `RESPONSE_STRING_KEYS` in serial.js, handed to callers as JSON text) and optional `mac0..mac5`, sent as its own message (`CMD.SET_MAC`) before set-network because the firmware's 100-byte request buffer truncates a combined message (the OUI `mac0..mac2` is fixed at `00:08:DC`, the W5500's WIZnet block: `netinfo.macProblem()` and the firmware both refuse any other; only the last three bytes are editable, in Admin -> Network `#networkMac` only). `netinfo.readControllerInfo()` runs on every connect (`serial.onConnected`) and after writes; a controller that never answers is `supported:false` ("Not reported by this firmware"), but a timeout from one that has answered before is treated as transient. `calibration.setNetwork` over USB reads netinfo/macinfo back and reports `acknowledged` only on a match; over Ethernet it cannot (the link drops). The relay `snapshot()` never includes `state.network` or the MAC/IP. Tests: `npm run test:netauth` (`tools/netauth-selftest.js` + `tools/netauth-integration.js` against `tools/mock-controller.js`) and `python tools/firmware-auth-test/run.py` (embedded firmware C under gcc with stubs; `patch-fcfx.js` there re-creates the `.fcfx` edits from `Firmware/Archive/pre-auth-backup/`). If Electron starts as plain Node from your shell, unset `ELECTRON_RUN_AS_NODE`.
- Admin -> **Network** tab (`renderer/index.html` `#networkTab`, `app.js` `renderNetworkStatus`/`refreshNetworkSettings`) is laid out for a non-expert: a status banner (`describeNetworkState`/`renderNetHero` in `app.js`: one plain sentence for the current link plus at most one next-step button that opens and focuses the control that fixes it), then one card, "Connect over the network": a single IP field (the address read off the controller's touchscreen) and a **Connect** button (`saveEthernet`: saves the host and switches network use on); the on/off tick, port and "Find Controller Automatically" scan sit under *Advanced*. Two collapsed `<details>` sections follow: controller address/port/MAC (read-back + edit, the technical settings) and sharing with other PCs (relay + remote client). Element IDs are the contract with `app.js`: keep them if the markup is rearranged. Raw refusal messages from `state.network.ethernetBlocked` go to the activity log, not the card; the banner words them. The tab used to be five equal cards of jargon, then had a key-management card, which operators found complicated. All `network:*` IPC handlers are `adminOnly` in `main.js`.

### Simulation mode

`--simulate` (or `WIND_TUNNEL_SIMULATION=1`) makes `state.simulation = true` at startup. `serial.setFanSpeed`/`setAngle`/`readSensorsOnce` short-circuit to `state.simulateSensors()` (in `main/state.js`) instead of touching the real port, so sweeps and the sensor-sample timer work unchanged in simulation — they just never hit `sendBinary`. Production (`npm start` with no flag) must never silently fall into this mode.

### Experiments, sweeps, and logging

`main/experiments.js` is a single declarative table (8 entries) read by both `main.js`'s `experiment:list` handler and `main/sweeps.js`/`main/logging.js`. **`dragShape` and `tapping` are metadata only** — the Flowcode source they're derived from has no coefficient formula (no density/area/`0.5*v²` anywhere) and no per-shape correction factor, so "Lift/Drag Coefficient" experiments log the raw sensor float as-is. Never make a calculation read `state.dragShape` or `state.tapping` — they only belong in the CSV-row builder (`sweeps.js`'s `buildRow()`) and the UI label.

Each experiment is exactly one of three logging shapes, matching the legacy Flowcode source's own timer wiring and `OnLogButtonClick` switch (`Wind Tunnel Control.fcsx`):
- **Sweep-driven** (`sweepType: 'angle'|'fan'`: `liftCoefficient`, `stemRacing`) — one point/CSV row per sweep tick, from `sweeps.js`'s `tick()`.
- **Continuous** (`sensorsVsTime` only) — one point/CSV row per sensor-sample tick while `state.logging.active`, from `startSensorSampleTimer`. This is the *only* no-sweep experiment the legacy source auto-logs on a timer (its own timer 6 only calls `OnLogButtonClick` automatically when `Exercise = 6`).
- **Manual** (`manualLog: true`: `pressureToVelocity`, `pressureTappedCylinder`, `pressureTappedAerofoil`, `dragCoefficient`, `custom`) — one point per `sweeps.js`'s `logPoint()` call (IPC `experiment:logPoint`, fired by the renderer's "Log Point" button), mirroring the legacy source's single "Log" button: a chart point is always added, a CSV row only if a log file is open, and the driven value (fan speed / manual angle / tapping channel) auto-advances by its configured increment for the next click. Convert Pressure to Velocity shares the same `fanSpeedIncrement` field/variable as Drag Coefficient (`Wind Tunnel Control.fcsx:1528` and `:1722` both read the same `IncrementSpeed` variable), even though that property is filed under Drag Coefficient's property folder in the legacy source.

`sweeps.js` runs up to two independent timers (never more than one sweep at a time): the sensor-sample timer (`startSensorSampleTimer`, skips its own read while a sweep tick is active to avoid duplicate serial round-trips) and the active sweep timer (`startAngleSweep`/`startFanSweep`). A sweep **auto-stops at `end` and resets `current` to `start` — it never reverses or loops**; manual `stopSweep()` resets to `start` too, for consistency. Tapping channel auto-advances by `tapping.increment` after each logged point and wraps `23 -> 1`.

`logging.js` writes `WindTunnelLog_<timestamp>.csv` using the active experiment's `csvColumns` as the columns (the header row shows each as a name plus unit, e.g. `Lift (mN)`, via `COLUMN_HEADERS` in `logging.js`; custom X/Y take the picked axes' names/units), to a folder persisted in `wind-tunnel-config.json` (separate file from the admin credential). `appendRow()` is called from the sweep tick for sweep-driven experiments, from the sensor-sample timer for `sensorsVsTime`, and from `logPoint()` for the manual experiments.

### Admin / security

- Admin credential is a scrypt hash + random salt in `wind-tunnel-admin.json` under Electron's `userData` path (`main/admin.js`). Plaintext password is never persisted or logged. **Every fresh install (no file) uses the same initial password**, kept in `admin.js` only as the salted hash `DEFAULT_RECORD` (owner's decision 2026-11-10, after installers each typed a different first password because the first-typed one used to become the Admin password); `Change Password` in Admin -> Settings replaces it with a per-PC file, and the change is optional, not forced. `readAdminRecord()` returns the default only on `ENOENT`; any other read failure is `unreadable`, so a damaged install never falls back to the default. Deleting `wind-tunnel-admin.json` resets a PC to the initial password. `setup()` is now unreachable from the UI (`status().configured` is always true). The file is additionally wrapped with Electron `safeStorage` (Windows DPAPI) as `{v:2, enc}` when available; legacy bare `{salt,hash}` files are only re-saved wrapped on setup/change-password, never on verify (older builds share this file under the same `userData` folder and cannot read the wrapped format -- they throw `ERR_INVALID_ARG_TYPE` in `admin:verify`). A file that exists but can't be read/decrypted reports `unreadable` (never "not configured", which would let the next typed password become the Admin password). `admin.changePassword(current, new)` (`admin:changePassword`, Admin -> Settings tab) re-verifies the current password, enforces >= 8 chars, and re-hashes with a fresh salt. `admin.unlock()` sets a 30-minute expiry (`SESSION_TIMEOUT_MS`); `isUnlocked()` is checked lazily (no background timer) and is the **authoritative** gate for calibration writes — `main/calibration.js`'s `guard()` checks `admin.isUnlocked()` and `!state.sweep.running` server-side, not just in the renderer (the renderer's own checks are fast-path UX only, bypassing them must not be enough to write calibration).
- **Bootloader protocol** (`main/bootloader.js`, orchestrated by `main/firmware.js`): ported **verbatim** from `../Process Control V2/main.js`'s bootloader IPC handlers (its persistent-USB-HID-connection model, CRC table/algorithm, frame escaping, Intel-HEX handling, batching, and every timeout/retry value), at the owner's explicit request to bring the logic over "as it is" rather than fixing anything, including a latent bug described below. `main/bootloader.js` keeps the device handle open across calls (`connect()`/`disconnect()`) instead of opening/closing it per action — Control and Calibrator-style "one open session" rules don't apply here since the bootloader is a separate USB HID identity from the running application, but within a bootloader session the same open handle is reused by every subsequent action until the operator disconnects or `run()`/`JMP_TO_APP` succeeds (mirroring Process Control V2's `usbHidDevice` module-scope state). The protocol: 64-byte HID reports (report ID `0x00` + 64 data bytes); each command frame is `SOH(0x01) + [cmd byte + payload + CRC16LE] with SOH/EOT(0x04)/DLE(0x10) byte-stuffed + EOT`; commands are `READ_BOOT_INFO=1`, `ERASE_FLASH=2`, `PROGRAM_FLASH=3`, `READ_CRC=4`, `JMP_TO_APP=5`; the CRC is a CRC-16/XMODEM-style nibble-table checksum (`calculateBootloaderCRC` in Process Control V2, ported as `calculateCrc` in `bootloader.js`). `PROGRAM_FLASH` batches `RECORDS_PER_COMMAND = 10` raw Intel-HEX records per HID exchange, fire-and-forget (no response wait, no retry, matching Process Control V2 exactly) with a 2ms pause between batches; `READ_CRC`/`verify` sends a CRC/address/length computed locally from the loaded hex file (mirroring Process Control V2's `calculateFlashCRCFromHexFile`, which processes every line in the file, not just data records) and the device's returned CRC must match before `verify` reports success. Per-command timeouts/retries also match Process Control V2 exactly: `readInfo` 3 retries/200ms, `erase` 3 retries/5000ms, `readCrc` 3 retries/2000ms, `run`/`JMP_TO_APP` 1 attempt/10ms with no response required; connecting polls for the USB HID device up to 10 times, 500ms apart (it may still be enumerating right after a bootloader-mode trigger). `JMP_TO_APP` is fire-and-forget and closes the persistent connection afterward (the device disconnects itself once it jumps).
  - **Known, intentionally-unfixed bug carried over from Process Control V2**: `computeVerifyInfo()`'s virtual-flash scratch buffer (`FLASH_SIZE`) is exactly `5 * 1024 * 1024` bytes — smaller than `BOOT_SECTOR_BEGIN` (`0x7FC000`, ~8.37 MB). This is a latent buffer-overflow bug in the original C++ bootloader tool that Process Control V2's JS port reproduces, and the owner explicitly asked for this app to reproduce it too rather than fix it (do not re-enlarge this buffer). The write into that undersized buffer is a bounds-checked per-byte loop rather than `Buffer.copy()` purely so the host doesn't crash with a `RangeError` — bytes landing at or past `FLASH_SIZE` are silently dropped instead, which is the same *effective* behavior as the original bug (a wrong/short CRC for hex files whose data lands above 5 MB), not a fix of it.
  - The host-side ASCII-hex-to-binary conversion was written cleanly rather than replicating a latent CRLF-handling bug in the original tool's `ConvertAsciiToHex` (that bug could append a garbage trailing byte per record on CRLF-terminated hex files) — this only changes what the *host* parses from the file on disk, not anything about the wire protocol, and was already true before this port.
  - **UI behaviour (Admin → Bootloader):** the PID field is pre-filled with `0xA1` (the default in Process Control V2's Electron bootloader screen, `index.html` `usbPidInput`; an unverified guess for Wind Tunnel; still editable). `bootloader.connect()` deviates from the port in one way: if the entered PID never appears but exactly one other HID product ID (not the application's `0xF010`) exists under the VID, after 3 polls it opens that one and returns its real PID, which the renderer writes back into the PID field. Once the real bootloader PID is seen on hardware, record it here. Trigger Bootloader has no confirm popup, is enabled only while the application link is up (not simulation/remote), and after a successful trigger stays grey until the link has dropped and come back (`noteHardwareState()` in `renderer/app.js`; 20 s fallback if the controller ignores the command).
  - **The bootloader's USB PID is NOT confirmed.** The application firmware identifies as VID `0x12BF` / PID `0xF010` (documented in `../AGENTS.md`), but nothing in this codebase confirms the *bootloader* enumerates under the same PID — PIC32 USB bootloaders commonly use a different PID than the running application (Process Control V2's own bootloader uses PID `0x010C` vs. its application's `0x0113`, both under VID `0x12BF`), and the Wind Tunnel Flowcode firmware source only documents the application's identity. `main/bootloader.js` therefore takes VID/PID as required call parameters with no bootloader PID default — the Admin → Bootloader tab's "Communication settings" card has the operator enter both (VID defaults to `0x12BF`; PID has no default and must be read from Windows Device Manager while the controller is in bootloader mode). **Before first use, confirm the real bootloader PID this way and record it here.**
  - Firmware actions (`checkDevice`/`connect`/`loadHex`/`readInfo`/`erase`/`program`/`readCrc`/`jumpToApp`, exposed as `admin:bootloaderCheckDevice`/`admin:bootloaderConnect`/`admin:bootloaderLoadHex`/`admin:bootloaderReadInfo`/`admin:bootloaderErase`/`admin:bootloaderProgram`/`admin:bootloaderReadCrc`/`admin:bootloaderJumpToApp`/`admin:bootloaderDisconnect`) all require `admin.isUnlocked()` first (`main/firmware.js`'s `guarded()` wrapper, the same role its old `guard()` played), per `../AGENTS.md`'s requirement that device detection, erase, programming, and verification each need password confirmation — Process Control V2 has no such gate; it is layered on top of the ported logic. The renderer drives a Connect/Disconnect toggle (`#connectBtn`) and a client-side Erase→Program→Verify sequence (`#eraseProgramVerify`'s click handler in `renderer/app.js`, mirroring Process Control V2's `eraseProgramVerify()`) rather than a single generic action dispatch. Windows UAC elevation for erase/program is still the pre-existing stub in `main.js` (`admin:requestElevation` always declines) — that part of `../AGENTS.md`'s firmware-flashing requirement is not wired up yet; don't assume elevation is enforced.
  - **Trigger Bootloader** (`firmware.triggerBootloader`, `admin:bootloaderTrigger`, `#triggerBootloaderBtn`) sends `{"BL":1}` over the application serial link, exactly as Process Control V2's `send-bootloader` handler does (`CMD.ENTER_BOOTLOADER` = `'N'` in `protocol.js`, encoded in `serial.js`'s `jsonRequestFor()`; no reply expected). It is admin-gated like every other firmware action, refused in simulation / when disconnected / during a sweep, and stops the fan first. **The key was taken from Process Control V2, and V2.0.7's firmware source does handle it** (verified in `../Firmware/WindTunnel V2.0.7.c`, `FCM_ParseJSON()`: `FindName("BL")` matches on the key name only, so the value is ignored; it draws "Bootloader Mode" on the display, waits 10 ms and resets the MCU with no reply — the same path as the touchscreen "Bootloader" menu entry). It is not in `WindTunnelAPI 1.xlsx`, and V2.0.2–V2.0.5 have no such handler. **Not yet exercised on real hardware**, and the controller must be running V2.0.7 or later. If the controller ignores `{"BL":1}` (older firmware), use the touchscreen entry and click Connect as before. `firmware.js` therefore depends on `serial.js` + `protocol.js` as well as `bootloader.js`/`admin.js`/`state.js`.
  - None of this has been exercised against real hardware (no automated test suite, no bootloader-mode device available during implementation) — static syntax checks and a `--simulate` boot pass, but hardware-in-the-loop verification of erase/program/verify/run is still required before relying on it.
- Calibration writes that have a hardware readback command are confirmed by reading back, and the UI must only show a value as saved after `acknowledged: true` comes back, never optimistically. Scalers (`H`→`I`): `setScaler` validates channel/mode/factor (plain decimal text only, non-zero, finite, ≤1e6; Relative may not drive the stored value to 0), reads the current scaler, writes `senscch`,`senscale`,`senscmode` in that order with the factor as a 6-decimal number (the legacy encoding; never a widened float32; `serial.js` `encodeRequest()` appends `.000000` to a whole-number `senscale` because the firmware's `FCI_STRING_TO_FLOAT` drops the sign of `-1` written without a decimal point -- not yet re-checked on hardware), waits 100 ms, re-reads, and is `acknowledged` only if the controller reports what the firmware rule predicts (Absolute: `Scaler = factor`; Relative: `Scaler = factor * Scaler`). Read-backs are rounded to 6 dp; the renderer resets the mode select to Absolute after a save or refresh so a Relative factor can't be applied twice. The velocity LUT is different: `setLutTable` writes all ten `J` entries (50 ms apart), waits 150 ms, then does ONE `K` read-back and is `acknowledged` only if every entry matches within 0.011 (firmware reports 2 dp). Never save/read back entry-by-entry: V2.0.6 answers `getvlu` with TWO JSON objects (`vl0`–`vl4`, then `vl5`–`vl9` ~5 ms later) which `serial.js` merges, and an immediate read returned stale/NaN entries that overwrote the operator's typed values. `serial.js` also ignores any reply object that lacks the pending command's key, so a late half of a `getvlu` reply cannot resolve another command. On a failed or mismatched save the renderer keeps what the operator typed.
- Admin LUT card: per fan step a Pressure (Pa) → Velocity (m/s) row; Zero Sensor (reuses `device:zeroSensors`), Start capture, and an operator-typed pressure per row: Enter converts it to velocity and the renderer moves the fan to the next 10 % via `calibration:setLutFan` (Enter after 100 % stops the fan); clicking a "Fan N%" label jumps the fan to that step. A single Save Table sends everything. Velocity = √(2·|P|/ρ), ρ = 1.20 kg/m³ (`AIR_DENSITY` in `renderer/app.js`, from `../CP0704-Aerodynamics.pdf` Worksheet 1; `../Wind tunnel - Test Results report.pdf` used 1.225). Pressure is renderer-only working data — only the ten velocities go to the controller. `setLutFan(0)` is exempt from the admin gate so an expired session can never strand a running fan.

### Renderer conventions

- `renderer/app.js` uses a single `$(id)` helper and a flat `state` object for renderer-only concerns (`liveSamples`, `experimentHistory`, `currentExperiment`, `hexPath`). For sweep-type experiments, `experimentHistory` is only appended to while `value.sweep.running` is true (from the pushed state). For `manualLog` experiments (`pressureToVelocity`, `pressureTappedCylinder`, `pressureTappedAerofoil`, `dragCoefficient`, `custom`), a point is appended only when `value.loggedPointSeq` has moved on from `state.lastLoggedPointSeq` — i.e. once per "Log Point" button click (`main/sweeps.js`'s `logPoint()`), using the row it put in `value.lastLoggedPoint`. `sensorsVsTime` is the only no-sweep experiment that stays continuous, and it never uses `experimentHistory` at all (`updateChartVisibility()` shows the live chart for it instead). `experimentHistory` represents the experiment's accumulated plot, not the rolling live buffer (`liveSamples`), and must stay independent of it. The manual, non-custom experiments above also declare an `xField` in `main/experiments.js` (`fanSpeed`/`manualAngle`/`tappingX`; the pressure-tapped experiments plot raw pressure in Pa, no Cp) so `charts.js`'s `updateHistory()` plots the real swept value on the x-axis instead of a plain sample index, matching the legacy XY plot.
- Theme is applied via `document.documentElement.setAttribute('data-theme', 'dark'|'light')` (not a body class) because `matrix-ui.css`'s DaisyUI tokens key off `[data-theme]`; preference persists to `localStorage['wind-tunnel-theme']`.
- Charts go through `renderer/charts.js`'s `WindTunnelCharts` — `configureForExperiment()` rebuilds both chart's datasets from the experiment's `liveTraces` whenever the experiment selector changes; `updateLive`/`updateHistory` are called from `app.js`'s `render()` on every `state:update` push. Never feed `historyChart` from `liveSamples`.
